# Vue.js Checkin Page — Complete Use Cases

## API Architecture

### Endpoints

```
GET  /checkins/availability                        → Pre-flight check (no side effects; for third-party integrations)
POST /checkins                                     → Create checkin (calls AddReturn; always creates a record unless blocked)
POST /checkins/{checkin_id}/hold_confirmation      → Confirm the trapped hold (set waiting or transfer)
POST /checkins/{checkin_id}/hold_cancellation      → Cancel the trapped hold
POST /checkins/{checkin_id}/transfer_confirmation  → Confirm transfer (set in transit)
POST /checkins/{checkin_id}/transfer_cancellation  → Cancel pending transfer
POST /checkins/{checkin_id}/recall_confirmation    → Confirm recall (set waiting or transfer)
```

### Flow: Happy path (item was checked out, no holds/transfers)
```
Client: POST /checkins { external_id: "123456", library_id: "CPL" }
Server: 200 { checkin_id: 42, checkout_id: 99, messages: [], ... }
         + X-Koha-Module-Policy: <jwt>
         (done — one round trip)
```

### Flow: Item not checked out (needs confirmation)
```
Client: POST /checkins { external_id: "123456", library_id: "CPL" }
Server: 412 { error_code: "confirmation_required", confirms: { NotIssued: "123456" }, confirmation_token: "jwt..." }

Client: POST /checkins { external_id: "123456", library_id: "CPL" } + ?confirmation=jwt...
Server: 200 { checkin_id: 42, local_use: true, messages: [{ message: "not_issued" }], ... }
```

### Flow: Hold found (requires staff decision)
```
Client: POST /checkins { external_id: "123456", library_id: "CPL" }
Server: 200 { checkin_id: 42, hold_id: 7, messages: [{ message: "hold_found", payload: { status: "reserved", ... } }] }
         (checkin created, item returned, but hold NOT yet set to waiting)

         Staff sees modal → decides to confirm
Client: POST /checkins/42/hold_confirmation
Server: 201 { checkin_id: 42, hold_id: 7, transfer_id: null | 15, ... }
         Location: /api/v1/checkins/42
         ($checkin->confirm_hold called — ModReserveAffect + transfer if needed)
```

### Flow: Transfer needed (requires staff acknowledgment)
```
Client: POST /checkins { external_id: "123456", library_id: "CPL" }
Server: 200 { checkin_id: 42, transfer_id: 15, messages: [{ message: "needs_transfer", payload: { to_library: "BRB" } }] }

         Staff confirms transfer
Client: POST /checkins/42/transfer_confirmation
Server: 201 { ... }
         Location: /api/v1/checkins/42
         ($checkin->confirm_transfer — sets transfer in transit)
```

### Flow: Staff cancels a trapped hold
```
Client: POST /checkins/42/hold_cancellation { reason: "PATRON_REQUEST" }
Server: 201 { checkin_id: 42, hold_id: null, ... }
         Location: /api/v1/checkins/42
         ($checkin->cancel_hold — hold cancelled, hold_id cleared)
```

### Key design decisions

1. **POST always creates the checkin** (unless blocked by 403). AddReturn runs immediately.
   The hold/transfer/recall is flagged in messages but NOT acted upon — staff decides via PUT.
   The checkin record is created for every scan (including blocked ones) for audit trail.
   The `interface` column records the source (intranet, api, sip, cron, commandline).

2. **Sub-resource confirmation endpoints** handle post-checkin decisions. Each is a
   separate POST endpoint returning 201 + Location header. Most checkins (happy path)
   complete in a single POST to /checkins. The sub-resources are only called when a
   modal requires staff action:
   - `POST /checkins/{id}/hold_confirmation` — sets hold to waiting (or creates transfer)
   - `POST /checkins/{id}/hold_cancellation` — cancels the hold (with optional reason)
   - `POST /checkins/{id}/transfer_confirmation` — sets transfer in transit
   - `POST /checkins/{id}/transfer_cancellation` — cancels transfer
   - `POST /checkins/{id}/recall_confirmation` — sets recall to waiting (or starts transfer)

3. **X-Koha-Module-Policy JWT** is returned on every response via the
   `Koha::REST::Plugin::Policy` helper. The JWT is generated by
   `Koha::Module::Policy::Checkin` using `Koha::Token->encode_claims` (Bug 43077).
   The client decodes the payload to know what UI controls to show
   (exempt_fine checkbox, date picker, etc.). 19 capability keys covering fines,
   holds, recalls, transfers, display, and blockers.

4. **Embeds** (`x-koha-embed` header) allow the client to request nested data in a
   single call: `hold`, `hold.patron`, `transfer`, `transfer.to_library`,
   `recall`, `recall.patron`, `item`, `item.biblio`, `checkout`, `user`, etc.

5. **GET /checkins/availability** exists for third-party pre-flight checks (self-check
   machines, RFID gates) but is NOT in the Vue page's critical path.

### Hydration strategy

The checkin UI is a **Vue island** — a custom element (`<circ-checkin>`) mounted
inside the standard Koha TT shell via the existing islands hydration system in
`main-container.inc`. This gives us sidebar, breadcrumbs, and header for free.

```
Page load (GET /cgi-bin/koha/circ/checkin.pl)
  └── .pl controller calls get_template_and_user (auth + shell chrome)
  └── Builds Koha::Module::Policy::Checkin->new({ user => $patron, library => $branch })
  └── Serializes policy as JSON string → template variable
  └── checkin.tt renders <circ-checkin library-id="CPL" module-policy="...">
  └── main-container.inc hydrate() detects the element, lazy-loads the chunk
  └── Vue island mounts, reads props, initializes store
```

**Template integration:**
```html
[% SET aside = Koha.Preference('CircSidebar') ? 'circ-nav' : '' %]
[% WRAPPER 'main-container.inc' aside=aside %]
    <circ-checkin
        library-id="[% Branches.GetLoggedInBranchcode | html %]"
        module-policy="[% module_policy_json | html %]"
    ></circ-checkin>
[% END %]
```

**Store initialization from props:**
```js
// Main.vue receives props from custom element attributes
props: { libraryId: String, modulePolicy: String }

// On mount, initializes the Pinia store
onMounted(() => {
    store.init({ policy: props.modulePolicy, libraryId: props.libraryId });
});
```

**Why a Vue island (not a full-page app like ERM):**
- Checkin is a single view — no client-side routing needed
- The page needs the left sidebar (`circ-nav`, conditional on `CircSidebar` pref)
- The header checkin search box can dispatch barcodes to the island via CustomEvent
  instead of navigating to a new page
- Lazy-loaded: the ~112KB chunk only loads when `<circ-checkin>` is in the DOM
- Follows the established pattern (admin-menu, vendor-menu, etc.)

**Refresh mechanism:**
- Every POST/PUT response carries `X-Koha-Module-Policy` JWT header
- Client decodes and compares with current state; updates reactively if changed
- Any 403 response → hard page reload (forces re-hydration via the .tt shell)
- This handles permission changes, preference toggles, or session expiry mid-session

**Header search box integration (future):**
- The `checkin-search-box.inc` form can be intercepted with a small JS snippet
- When already on the checkin page: prevent form submit, dispatch barcode to the
  `<circ-checkin>` island via CustomEvent on the element
- Avoids a full page reload for each barcode when you're already on the page

## 1. Core Checkin Flow

### UC-1.1: Scan barcode to check in item ✅
- **Description:** Staff scans or types an item barcode to initiate check-in
- **Trigger:** Barcode entered in text input + Enter key or "Check in" button click
- **User sees/does:** Types barcode, presses Enter; system processes return via `POST /checkins` with `external_id`
- **Gates:** `circulate: circulate_remaining_permissions`
- **Priority:** Must-have (core flow)

### UC-1.2: Successful check-in result ✅
- **Description:** Item is returned successfully; row added to checked-in items table
- **Trigger:** API returns 200 with `checkout_id` populated
- **User sees/does:** Item appears in table with due date, title, patron info; barcode field clears and re-focuses
- **Gates:** None (always shown on success)
- **Priority:** Must-have (core flow)

### UC-1.3: Item not currently checked out (not issued) ✅
- **Description:** Scanned item has no active checkout
- **Trigger:** API returns 412 with `NotIssued` confirmation key; or message `not_issued` in 200 response
- **User sees/does:** Confirmation dialog "This item is not checked out. Check in anyway?"; if confirmed, re-sends POST with JWT confirmation token
- **Gates:** None
- **Priority:** Must-have (core flow)

### UC-1.4: Local use recorded ✅
- **Description:** Item not on loan is checked in; local use counter incremented
- **Trigger:** `local_use: true` in response + message `local_use`
- **User sees/does:** Info message "Local use recorded" displayed
- **Gates:** `RecordLocalUseOnReturn` syspref (backend logic)
- **Priority:** Must-have (core flow)

### UC-1.5: Prevent double submission ✅
- **Description:** Prevent accidental double-scan of same barcode
- **Trigger:** User presses Enter twice quickly
- **User sees/does:** Submit button disabled after first click until response received
- **Gates:** None
- **Priority:** Must-have (core flow)

### UC-1.6: Module policy initialization ✅
- **Description:** On page load, fetch module policy to configure UI capabilities
- **Trigger:** Page mount / first API response `X-Koha-Module-Policy` JWT header
- **User sees/does:** UI controls conditionally shown/hidden based on decoded policy (exempt fines checkbox, date override, etc.)
- **Gates:** None (policy always returned)
- **Priority:** Must-have (core flow)

### UC-1.7: Barcode input auto-focus ✅
- **Description:** Barcode input receives focus on page load and after each check-in completes
- **Trigger:** Page load, modal dismiss, successful/failed check-in processing
- **User sees/does:** Cursor always returns to barcode field for continuous scanning
- **Gates:** None
- **Priority:** Must-have (core flow)

## 2. Checkin Options

### UC-2.1: Dropbox / Book drop mode
- **Description:** Enables book drop mode; system calculates return date as last open day before today
- **Trigger:** Staff checks "Book drop mode" checkbox
- **User sees/does:** Checkbox toggled; barcode input gets visual warning style (highlighted border); `dropbox_mode: true` sent with each POST
- **Gates:** Policy `dropbox_mode` (always available per backend)
- **Priority:** Must-have (core flow)

### UC-2.2: Forgive overdue fines (exempt fine)
- **Description:** Exempts overdue charges for the returned item
- **Trigger:** Staff checks "Forgive overdue charges" checkbox
- **User sees/does:** Checkbox toggled; barcode input gets visual warning style; `exempt_fine: true` sent with POST
- **Gates:** Policy `exempt_fine` (requires `finesMode=production` + `updatecharges: writeoff` permission)
- **Priority:** Must-have (core flow)

### UC-2.3: Return date override
- **Description:** Staff specifies a custom return date (backdating)
- **Trigger:** Staff enters date in date picker (flatpickr equivalent)
- **User sees/does:** Date picker shown (only past dates allowed, with time); `return_date` (ISO 8601) sent with POST
- **Gates:** Policy `specify_return_date` (requires `SpecifyReturnDate` syspref)
- **Priority:** Must-have (core flow)

### UC-2.4: Remember return date override
- **Description:** Persists the override date across multiple check-ins in the session
- **Trigger:** Staff checks "Remember for next check-in" checkbox
- **User sees/does:** Date persists in field after each check-in until unchecked or cleared
- **Gates:** `SpecifyReturnDate` syspref
- **Priority:** Enhancement

### UC-2.5: Forgive fees for manually expired holds
- **Description:** Forgives charges when a hold expires due to manual expiration
- **Trigger:** Staff checks "Forgive fees for manually expired holds" checkbox
- **User sees/does:** Checkbox visible only when relevant; passed as parameter in hold-related operations
- **Gates:** Policy `forgive_hold_fees` (requires `ExpireReservesMaxPickUpDelayCharge` + `updatecharges: writeoff`)
- **Priority:** Enhancement

### UC-2.6: Circ settings panel toggle
- **Description:** Show/hide the circulation settings panel (date override, checkboxes)
- **Trigger:** Staff clicks settings toggle button
- **User sees/does:** Panel expands/collapses revealing checkin options
- **Gates:** None
- **Priority:** Must-have (core flow)

## 3. Item Status Alerts

### UC-3.1: Lost item — blocked ✅
- **Description:** Item has lost status and system blocks check-in
- **Trigger:** API returns 403 with blocker `BlockedLost`
- **User sees/does:** Error message "This item is lost and cannot be checked in"; item NOT checked in
- **Gates:** `BlockReturnOfLostItems` syspref enabled
- **Priority:** Must-have (core flow)

### UC-3.2: Lost item — allowed (was lost)
- **Description:** Item was lost but check-in proceeds; item marked found
- **Trigger:** Message `was_lost` in 200 response
- **User sees/does:** Info/warning message "Item was [lost status], now found" with possible fee adjustment messages
- **Gates:** `BlockReturnOfLostItems` syspref disabled
- **Priority:** Must-have (core flow)

### UC-3.3: Withdrawn item — blocked ✅
- **Description:** Item is withdrawn and system blocks check-in
- **Trigger:** API returns 403 with blocker `BlockedWithdrawn`
- **User sees/does:** Error message "This item has been withdrawn and cannot be checked in"
- **Gates:** `BlockReturnOfWithdrawnItems` syspref enabled
- **Priority:** Must-have (core flow)

### UC-3.4: Withdrawn item — warning only
- **Description:** Item is withdrawn but check-in proceeds with warning
- **Trigger:** Message `withdrawn` (type: warning) in 200 response
- **User sees/does:** Warning "Item has been withdrawn" with status description; item still checked in
- **Gates:** `BlockReturnOfWithdrawnItems` syspref disabled
- **Priority:** Must-have (core flow)

### UC-3.5: Not-for-loan status updated on return
- **Description:** Item's not-for-loan status auto-updated per `UpdateNotForLoanStatusOnCheckin` mapping
- **Trigger:** Message `not_for_loan_status_updated` with payload `{ from, to }`
- **User sees/does:** Info message showing old→new status values
- **Gates:** `UpdateNotForLoanStatusOnCheckin` syspref (YAML mapping)
- **Priority:** Enhancement

### UC-3.6: Item location updated on return
- **Description:** Item's shelving location changed on check-in (e.g., CART → permanent location)
- **Trigger:** Message `item_location_updated` with payload
- **User sees/does:** Info message showing location change
- **Gates:** Backend logic (UpdateItemLocationOnCheckin-type behavior)
- **Priority:** Enhancement

### UC-3.7: Item belongs to a bundle
- **Description:** Checked-in item is a component of another item bundle
- **Trigger:** Message `in_bundle` with payload `{ host_item_id }`
- **User sees/does:** Warning "This item belongs to bundle [host barcode]" with "Remove from bundle" action button
- **Gates:** None
- **Priority:** Enhancement

### UC-3.8: Remove item from bundle
- **Description:** Staff removes a component item from its host bundle
- **Trigger:** Staff clicks "Remove from bundle" button on in_bundle warning
- **User sees/does:** Confirmation; API call `DELETE /api/v1/items/{host}/bundled_items/{component}`; success/failure feedback
- **Gates:** None (permission implied by circulation permission)
- **Priority:** Enhancement

## 4. Holds

### UC-4.1: Hold found — needs confirmation (same library)
- **Description:** A hold exists for the item and can be filled at the current library
- **Trigger:** Message `hold_found` with payload `{ status: "waiting" or "placed", library_id: current_library }`; embedded `hold` object
- **User sees/does:** Modal showing patron details (name, category, address, phone, email, restriction status), hold notes. Actions: "Confirm hold (Y)", "Print slip and confirm (P)", "Ignore (I)"
- **Gates:** None (core hold functionality)
- **Priority:** Must-have (core flow)

### UC-4.2: Hold found — needs transfer
- **Description:** A hold exists but pickup library is different from current library
- **Trigger:** Message `hold_found` with payload where `library_id != current_library`; embedded `transfer`
- **User sees/does:** Modal showing patron details + "Transfer to [library]". Actions: "Confirm hold and transfer (Y)", "Print slip, transfer, and confirm (P)", "Ignore (I)"
- **Gates:** None
- **Priority:** Must-have (core flow)

### UC-4.3: Hold found — already waiting
- **Description:** Item has a hold already in waiting status (re-check-in of waiting item)
- **Trigger:** Message `hold_found` with `status: "waiting"` on an item already set to waiting
- **User sees/does:** Modal with patron details + hold location + reserve notes. Actions: "Confirm hold (Y)", "Print slip and confirm (P)", "Ignore (I)", "Cancel hold (X)" with optional cancellation reason
- **Gates:** None
- **Priority:** Must-have (core flow)

### UC-4.4: Cancel a hold from checkin modal
- **Description:** Staff cancels the found hold instead of filling it
- **Trigger:** Staff clicks "Cancel hold (X)" in hold modal, optionally selects cancellation reason
- **User sees/does:** Dropdown of HOLD_CANCELLATION authorised values for reason; confirm action
- **Gates:** None
- **Priority:** Must-have (core flow)

### UC-4.5: Cancel all holds in hold group
- **Description:** Staff cancels all holds belonging to the same hold group
- **Trigger:** Staff clicks "Cancel all holds in hold group" button (visible when hold is part of a group)
- **User sees/does:** Confirmation dialog; API call `POST /api/v1/patrons/{id}/hold_groups/{id}/cancel`
- **Gates:** Policy `display_hold_groups` (requires `DisplayAddHoldGroups` syspref)
- **Priority:** Enhancement

### UC-4.6: Hold auto-filled
- **Description:** Hold was automatically filled on check-in without staff interaction
- **Trigger:** Policy `holds_auto_fill` enabled; hold filled silently; info message displayed
- **User sees/does:** Info banner showing patron details, hold/transfer info, print slip button
- **Gates:** `HoldsAutoFill` syspref
- **Priority:** Enhancement

### UC-4.7: Auto-print hold slip
- **Description:** Hold slip automatically sent to printer when hold auto-filled
- **Trigger:** Policy `holds_auto_fill_print_slip` enabled + hold auto-filled
- **User sees/does:** Print dialog triggered automatically (or slip sent to configured printer)
- **Gates:** `HoldsAutoFillPrintSlip` syspref
- **Priority:** Enhancement

### UC-4.8: Patron waiting holds notification
- **Description:** After check-in, notify staff that the patron has other holds waiting for pickup
- **Trigger:** Patron has waiting holds; policy `waiting_notify_at_checkin` enabled
- **User sees/does:** Info message "[Patron] has N hold(s) waiting for pickup" with link to patron account
- **Gates:** `WaitingNotifyAtCheckin` syspref
- **Priority:** Enhancement

## 5. Transfers

### UC-5.1: Item needs transfer (new transfer initiated)
- **Description:** Item needs to be sent to another library (home branch, floating, etc.)
- **Trigger:** Message `needs_transfer` with payload `{ to_library, trigger }`
- **User sees/does:** Modal "Please transfer this item to [library]". Actions: "Yes (Y)", "Yes, print slip", "No (N)"
- **Gates:** Policy `transfers_block` controls whether modal is blocking
- **Priority:** Must-have (core flow)

### UC-5.2: Transfer already initiated (acknowledge)
- **Description:** Transfer was automatically created; staff acknowledges
- **Trigger:** Message `transferred` with payload `{ transfer_id, to_library, trigger }`
- **User sees/does:** Modal "Item will be transferred to [library]". Actions: "OK (Y)", "Print slip (P)"
- **Gates:** Policy `transfers_block` controls blocking behavior
- **Priority:** Must-have (core flow)

### UC-5.3: Wrong transfer detected
- **Description:** Item was in transit to library A but arrived at library B
- **Trigger:** Message `wrong_transfer` (type: warning) with payload `{ to_library, item_id, trigger }`
- **User sees/does:** Warning modal "Wrong transfer detected, please return item to: [library]". Actions: "OK (Y)" (confirm redirect), "Print transfer slip (P)", "Cancel transfer (X)"
- **Gates:** `TransfersBlockCirc` controls blocking; `AutomaticConfirmTransfer` may auto-confirm
- **Priority:** Must-have (core flow)

### UC-5.4: Transfer arrived
- **Description:** Item that was in transit has arrived at its destination
- **Trigger:** Message `transfer_arrived` with payload `{ from_library }`
- **User sees/does:** Info message "Item received from [library]"
- **Gates:** None
- **Priority:** Must-have (core flow)

### UC-5.5: Auto-confirm transfer
- **Description:** Transfer modals automatically confirm when dismissed (non-blocking mode)
- **Trigger:** Policy `auto_confirm_transfer` enabled AND `transfers_block` disabled; modal dismissed
- **User sees/does:** Transfer confirmed silently on modal close
- **Gates:** `AutomaticConfirmTransfer` + `TransfersBlockCirc` off
- **Priority:** Enhancement

### UC-5.6: Print transfer slip
- **Description:** Staff prints a transfer slip for the item being sent to another library
- **Trigger:** Staff clicks "Print transfer slip" in transfer modal
- **User sees/does:** Print dialog / popup opens with transfer slip content
- **Gates:** None
- **Priority:** Must-have (core flow)

### UC-5.7: Cancel transfer
- **Description:** Staff cancels a pending or wrong transfer
- **Trigger:** Staff clicks "Cancel transfer (X)" in wrong transfer modal
- **User sees/does:** Transfer cancelled; item remains at current library
- **Gates:** None
- **Priority:** Must-have (core flow)

### UC-5.8: Wrong branch — complete block
- **Description:** Item cannot be returned at this library per AllowReturnToBranch policy
- **Trigger:** API returns 403 with blocker `Wrongbranch`; or message `wrong_branch`
- **User sees/does:** Blocking modal "This item must be checked in at [branch]" — NOT CHECKED IN. Only "OK" to dismiss.
- **Gates:** `AllowReturnToBranch` syspref
- **Priority:** Must-have (core flow)

### UC-5.9: Rotating collection transfer
- **Description:** Item needs transfer for rotating collection purposes
- **Trigger:** Transfer trigger reason = `RotatingCollection`
- **User sees/does:** Info message about rotating collection transfer with print slip option
- **Gates:** Rotating collections feature enabled
- **Priority:** Enhancement

### UC-5.10: Transfer trigger reason display
- **Description:** Show why a transfer was triggered in info banner and table
- **Trigger:** Any transfer message with `trigger` payload field
- **User sees/does:** Reason displayed (LibraryFloatLimit, Manual, StockrotationAdvance, StockrotationRepatriation, ReturnToHome, ReturnToHolding, RotatingCollection, Reserve, LostReserve, CancelReserve, TransferCancellation, Recall, RecallCancellation)
- **Gates:** None
- **Priority:** Enhancement

└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│  Koha::REST::V1::Checkins                                       │
│  REST controller. Validates input, calls domain methods,        │
│  renders responses. No business logic, no infrastructure.       │
│                                                                 │
│  Endpoints:                                                     │
│    GET  /checkins/availability                                  │
│    POST /checkins                                               │
│    POST /checkins/{id}/hold_confirmation                        │
│    POST /checkins/{id}/hold_cancellation                        │
│    POST /checkins/{id}/transfer_confirmation                    │
│    POST /checkins/{id}/transfer_cancellation                    │
│    POST /checkins/{id}/recall_confirmation                      │
└──────────────────────────────┬──────────────────────────────────┘
                               │ delegates to
┌──────────────────────────────▼──────────────────────────────────┐

│  Domain object. Owns the checkin record and its lifecycle.      │
│                                                                 │
│  Methods:                                                       │
│    confirm_hold      — ModReserveAffect + transfer if needed    │
│    cancel_hold       — $hold->cancel (reason optional)          │
│    confirm_transfer  — $transfer->transit                       │
│    cancel_transfer   — $transfer->cancel + revert recall        │
│    confirm_recall    — set_waiting or start_transfer            │
│                                                                 │
│  Relationships: item, hold, transfer, recall, checkout,         │

┌─────────────────────────────────────────────────────────────────┐
│  Koha::Module::Policy::Checkin                                  │

┌─────────────────────────────────────────────────────────────────┐
│  Koha::REST::Plugin::Policy                                     │

### Data flow: happy path

```
1. Page load
   └─ circ/checkin.pl → get_template_and_user + build policy
   └─ checkin.tt renders <circ-checkin library-id="CPL" module-policy="...">
   └─ main-container.inc hydrate() detects element → lazy-loads chunk
   └─ Main.vue mounts, calls store.init(props), BarcodeInput auto-focuses

2. Staff scans barcode
   └─ BarcodeInput emits "submit" with barcode string
   └─ Main.vue calls store.checkin(barcode)
   └─ store sets processing=true, calls API client
   └─ POST /checkins { external_id: barcode, library_id: "CPL" }
      └─ Controller defaults library_id from session
      └─ Availability check (blockers? → 403)
      └─ Confirmation needed? → 412 with JWT + item data
      └─ AddReturn runs → creates Koha::Checkin → attaches messages
      └─ Returns 200 + checkin object + X-Koha-Module-Policy header

3. Response handled (200 — success)
   └─ store adds entry to checkins[] with _status: "success" or "needs_action"
   └─ If hold/transfer/recall found → _status: "needs_action", modal auto-pops
   └─ Clears lastError, processing=false
   └─ Main.vue re-focuses BarcodeInput (never blocks scanning)

4. Response handled (412 — confirmation required)
   └─ store adds entry to checkins[] with _status: "pending_confirmation"
   └─ Stores _confirmation_token (JWT) and _confirms on the entry
   └─ Yellow row appears in table; modal auto-pops for first pending item
   └─ Staff confirms → store.confirmPending() re-POSTs with JWT → 200

5. Async scanning
   └─ Multiple barcodes scanned rapidly fire parallel requests
   └─ Responses fill the table as they arrive (success = normal, pending = yellow)
   └─ First pending item gets a modal; rest queue as yellow rows
   └─ After resolving modal, next pending item auto-pops
```

4. Display
   └─ CheckedInItems renders the new row
   └─ Message badges shown from checkin.messages[]
```

### Data flow: hold found

```
1. POST /checkins returns 200 with message "hold_found"
   └─ checkin.hold_id is set, hold embedded in response

2. (future) HoldModal opens showing patron details from hold.patron embed
   └─ Staff chooses: Confirm (Y) / Cancel (X) / Ignore (I)

3. Staff confirms
   └─ store.resolveAction(id, "confirm_hold")
   └─ POST /checkins/{id}/hold_confirmation
   └─ Controller checks hold_id present → calls $checkin->confirm_hold
   └─ Returns 201 + Location + updated checkin

4. Client updates checkin in store, closes modal, re-focuses input
```

### Policy refresh

```
Every API response carries X-Koha-Module-Policy JWT header.
Client decodes payload (base64, no secret needed) and compares
with current store.policy. If changed → reactive update.

On 403 → hard page reload (forces re-hydration from template).
```
